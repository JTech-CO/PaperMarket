# 운영·백업·복구 절차

이 문서는 단계 6에서 구현한 로컬 운영 도구와 운영자가 수행해야 하는 복구 절차를 구분합니다. 실제 Discord 접속, 공개 운영, 다른 물리 장치로의 복제, 디스크 고장·정전은 이 문서를 작성하면서 실행하지 않았습니다. 가상 기업·모의 원장 검증을 실제 금융 안전성 보증으로 사용하지 않습니다.

## 설정과 키

Node.js 24.20.0과 저장소의 고정 의존성으로 빌드합니다. `ACCOUNT_IDENTITY_KEY`·`MARKET_SEED`·`BACKUP_KEY`는 서로 독립적인 지속 서버 비밀입니다. `BACKUP_KEY`는 정확히 32바이트를 표현하는 64자리 hex입니다. 봇 명령·사용자 입력·로그·소스·명령행 인자로 키를 받거나 출력하지 않습니다. 보호된 서버 환경 또는 `.env`로 공급합니다. `.env`를 커밋하거나 원본 DB와 키의 유일한 사본을 함께 잃지 않도록 별도의 통제된 키 복구 사본을 보관합니다. 이 코드는 외부 비밀관리 서비스를 구성하지 않습니다.

| 설정 | 기본값·경계 |
|---|---|
| `PAPERMARKET_DATABASE_PATH` | 프로젝트 안의 `data/papermarket.sqlite` |
| `PAPERMARKET_BACKUP_DIRECTORY` | 프로젝트 안의 `data/backups`; 원본 DB를 포함하는 디렉터리 금지 |
| `PAPERMARKET_BACKUP_MIRROR_DIRECTORY` | 기본 비어 있음; 명시한 절대 로컬 경로만 일별 복제, 원본·기본 백업과 분리 |
| `BACKUP_KEY` | 필수 독립 AES-256 키; 실행 중 기존 사본의 키를 교체하지 않음 |

DB 경로·백업 경로는 운영자 설정입니다. Discord 요청이 경로나 백업 ID를 지정할 수 없습니다. UNC·상대 복구 경로·경로 구성요소의 `..`·심볼릭 링크/Windows junction·실제 경로의 이탈을 거절합니다. 작업 디렉터리는 `0700`, 파일은 `0600`으로 생성하지만 Windows ACL을 자동 구성한 것으로 간주하지 않습니다. 운영자는 실행 계정만 접근하도록 장비 ACL과 디스크 암호화를 설정해야 합니다. 원본 SQLite와 WAL·SHM은 이 도구가 암호화하지 않습니다.

## 정기 백업

기본 정책은 1시간마다 백업, 하루마다 설정된 복제 경로에 복제, 30일마다 복구 리허설입니다. 서버는 즉시 최초 주기를 점검한 뒤 1분마다 도래 여부를 확인합니다. 검증 작업은 별도 운영 워커에서 실행합니다. 성공 시각은 인증된 `schedule-v1.json`에 기록하여 정상 재시작 뒤 불필요하게 주기를 다시 시작하지 않습니다. 실패한 작업의 성공 시각은 갱신하지 않고 다음 점검에서 재시도합니다. 시스템 시계가 뒤로 가면 기존 성공 시각부터 간격이 충족될 때까지 기다립니다.

`BackupManager`는 타입이 제한된 `policy` 설정으로 주기와 보관 개수를 변경할 수 있습니다. Discord에서 이 정책을 변경하는 명령은 없습니다. 한 인스턴스의 중복 실행은 `BUSY`를 반환하고 디렉터리의 `ProcessLock`은 다른 프로세스의 동시 유지보수도 막습니다. 종료는 실행 중인 작업을 기다린 뒤 키의 메모리 사본을 지웁니다.

[SQLite Online Backup API](https://sqlite.org/backup.html)가 원본의 확정된 트랜잭션을 별도 스냅샷에 복사합니다. WAL 모드의 메인 파일만 복사하지 않습니다. 완성한 스냅샷은 쓰기 금지 연결에서 다음 항목을 검사합니다.

- SQLite 무결성·외래 키·현재 스키마와 마이그레이션 이름/체크섬, 지속 식별 키와 경제 시드의 결합
- 모든 활성·종료 계좌의 현금/수량 원장 재생·양측 균형·권리 해시·조건주문 예약/해제와 가용 자산
- 현재 및 과거의 경제 스냅샷 정규 JSON/해시·틱 연속성·기업 세대·가격·금리 구간, 현금이자 원금과 지급/현금 원장의 합계
- 보관된 모든 기준전략과 성과 표본의 실제 생산 코드 해시/원본 검증
- 고정된 전체 테이블의 행 개수·해시를 합친 상태 지문

검증 과정은 브로커 생성·마이그레이션·누락 기준전략 도입·성과 보완·금융 복구 쓰기를 하지 않습니다. 결과 지문에는 개별 Discord ID·계좌 ID·주문 토큰·경제 시드를 넣지 않습니다. 실제 행은 백업 안에 포함되어 암호화됩니다.

스냅샷을 AES-256-GCM으로 암호화하고 별도 파생 키로 manifest 전체를 인증합니다. 복호화 왕복·전체 지문 일치를 다시 검사한 뒤 암호문을 먼저, manifest를 마지막으로 게시합니다. manifest가 완성된 묶음의 표시입니다. 파일은 동기화한 뒤 같은 파일시스템의 임시 파일을 원자적으로 rename합니다. 이미 있는 이름을 덮어쓰지 않도록 이번 작업이 독점 생성한 빈 파일 예약만 교체합니다. Windows에서는 파일 동기화를 수행하지만 디렉터리 fsync와 실제 전원 차단 내구성을 검증했다고 주장하지 않습니다.

정상 종료·오류에서는 소유한 평문 임시 디렉터리를 제거합니다. `SIGKILL`·장비 중단에서는 `finally`가 실행되지 않을 수 있습니다. 다음 작업이 유지보수 잠금을 획득하면 인증된 `owner.json`·정확한 UUID 이름·실제 경로·허용 파일명을 확인하여 남은 작업 디렉터리를 제거합니다. 확인할 수 없는 디렉터리·심볼릭 링크·예상 밖 파일은 임의로 재귀 삭제하지 않습니다. 운영자는 해당 항목을 격리하고 원인과 개인정보 노출 여부를 확인해야 합니다.

## 보관과 복제

최근 24개 백업, 최근 7개 UTC 날짜의 대표 사본, 최근 4개 UTC 주간 구간의 대표 사본의 **합집합**을 유지합니다. 매시간 24개에 일별·주별 사본을 모두 따로 더하는 방식과 개수가 다를 수 있습니다. 첫 성공한 사본 이후 주기 점검에서 정리합니다. 정책에 맞춰 정리할 때도 인증된 manifest와 일반 파일인 자신의 묶음만 정확한 경로로 제거합니다. 무관한 운영 파일·손상 manifest·고아 암호문은 자동으로 지우지 않습니다.

명시된 복제 경로에 최신 성공 묶음을 하루마다 복사하고 암호 인증·복구 지문을 검증한 후 게시합니다. 복제 쪽에도 같은 보관 선택을 적용합니다. 서로 다른 폴더를 지정했다고 다른 물리 디스크나 지역으로 복제한 것은 아닙니다. 다른 장치의 마운트·권한·가용 공간·키 분리와 성공 상태를 운영자가 확인해야 합니다. 외부 저장 서비스·S3·메일/메신저 알림을 연결하지 않았습니다. 경로를 설정하지 않으면 복제를 수행하지 않습니다.

백업에는 생성 시점의 식별자·동의·알림·가명 금융 기록이 포함될 수 있습니다. `/close`가 현재 DB의 개인 데이터를 제거해도 이전 암호화 사본을 즉시 다시 쓰거나 전체 소거하지 않습니다. 사본은 위 선택 정책에 따라 교체됩니다. 오래된 사본을 복구하면 이후 처리한 종료·동의 철회가 되돌아갈 수 있으므로 운영자는 별도로 관리한 권리 요청 결과를 대조하고 봇을 재개하기 전에 다시 반영해야 합니다. 이 버전은 별도 삭제 등록부의 자동 병합이나 플랫폼 첨부·DM 파기를 구현하지 않습니다.

## 수동 검증과 복구

다음 명령은 **로컬 운영자 도구**입니다. 키를 인자로 넣지 않습니다. `.env`의 서버 비밀은 Node의 환경 파일 옵션으로 읽고 출력에는 성공 코드·백업 ID·시각·스키마·상태 해시·집계만 남습니다. 먼저 `npm run build`로 도구를 빌드합니다.

```powershell
node --env-file-if-exists=.env dist/src/ops/backup-cli.js create
node --env-file-if-exists=.env dist/src/ops/backup-cli.js verify <백업-ID>
node --env-file-if-exists=.env dist/src/ops/backup-cli.js rehearse <백업-ID>
node --env-file-if-exists=.env dist/src/ops/backup-cli.js verify-mirror <백업-ID>
```

복구는 다음 순서를 따릅니다.

1. Discord 봇과 금융/운영 워커를 정상 종료하고 다른 기록 프로세스가 실행 중인지 확인합니다. 살아 있는 원본 기록 잠금이 있으면 복구 CLI가 거절합니다. 잠금을 임의 삭제하거나 다른 프로세스를 강제 종료하는 자동 기능은 없습니다.
2. 최신 성공 백업의 manifest·암호문과 보호된 세 키를 준비합니다. 원본을 잃은 경우 명시된 복제 경로에서 `verify-mirror`로 검사할 수 있습니다. 원본 파일이 없어도 복구 도구는 새 파일을 생성할 수 있습니다.
3. 원본 DB와 같은 디렉터리 또는 설정된 백업 디렉터리의 **새 절대 `.sqlite`/`.db` 경로**를 지정합니다. 기존 파일·디렉터리·WAL·SHM·잠금 파일·백업 파일, 원본 경로, 해당 경로에 이미 붙은 WAL/SHM은 거절합니다.
4. 복호화한 임시 DB를 쓰기 금지로 검사하고 manifest의 전체 상태 지문과 대조합니다. 통과한 결과만 새 파일로 게시합니다. 검사 실패 시 새 DB를 게시하지 않습니다.
5. 종료·권리 요청·DM 철회 결과를 백업 시점 이후 기록과 대조하여 다시 반영하고 새 경로를 `PAPERMARKET_DATABASE_PATH`로 지정합니다. 계좌 개설·초기자금 재지급을 새로 실행하지 않습니다.
6. 원본/새 DB·WAL·잠금 위치, 시장 시각·예약·권리·기준전략·성과를 확인한 뒤 서버를 시작합니다. 시작 복구는 검증되지 않은 오프라인 시간을 경제 틱으로 무한 재생하지 않습니다. 이전 파일은 운영자가 정한 격리·보존·파기 절차로 처리합니다.

스키마 7은 기존 원장을 보존하며 정기 납입 계획과 납입 직전 평가 기록을 추가합니다. 기존 활성 계좌의 주기는 마이그레이션 당시 시장 틱부터 시작하고 과거 몫을 지급하지 않습니다. 백업 검증은 백업과 코드의 스키마가 같아야 합니다. 스키마 6 백업은 스키마 6 코드로 새 파일에 복원·검증한 뒤, 스키마 7 코드로 시작하여 마이그레이션합니다. 기존 백업을 덮어쓰지 않습니다.

```powershell
node --env-file-if-exists=.env dist/src/ops/backup-cli.js restore <백업-ID> 'C:\프로젝트\data\recovered.sqlite'
node --env-file-if-exists=.env dist/src/ops/backup-cli.js restore-mirror <백업-ID> 'C:\프로젝트\data\recovered.sqlite'
```

예시 경로는 실제 프로젝트의 새 파일 경로로 바꿉니다. CLI가 현재 실행 파일을 자동 교체하거나 봇을 재시작하지 않습니다. 복원 검사는 오래된 스키마를 자동 이행하지 않으므로 해당 백업과 일치하는 검증된 소스 버전에서 시작해야 합니다.

## 복구 목표와 검증의 한계

동일 장치의 프로세스 중단은 WAL·FULL 동기화·단일 기록자·트랜잭션·멱등성을 통해 확정 금융 작업을 재사용합니다. 응답 전달 전에 중단한 체결이 다시 확인되어도 금융 전표·체결을 두 번 만들지 않습니다. 커밋 전에 중단한 금융 작업은 전부 롤백됩니다. 디스크 자체를 잃으면 마지막 성공한 별도 사본 이후 기록은 복구할 수 없을 수 있습니다. 따라서 디스크 유실의 RPO를 0으로 선언하지 않습니다. 시간 단위 기본 사본과 일별 복제는 목표 주기이며 장비 장애·실패·중단 때의 실제 성공 시각을 함께 확인해야 합니다.

장기 reference·drift 배치와 생산 경제의 10,000틱 이력 검증은 아직 완료하지 않았습니다. 모형 품질은 NOT_CALIBRATED이며 짧은 pilot 결과로 장기 검증 완료를 판단하지 않습니다. 강제 프로세스 종료는 실제 정전이나 저장장치 손상을 대신하지 않습니다. Windows sandbox가 junction fixture 생성을 거절하면 테스트는 그 한계를 명시하며 실제 junction의 환경 검증 완료로 기록하지 않습니다. 복구 리허설은 임시 DB의 완전한 읽기 검증·지문 비교까지 수행하며 Discord 발송이나 금융 워커의 운영 재개를 자동 실행하지 않습니다.

## 상태 점검과 로그

```powershell
npm run health:check
```

이 명령은 Discord 연결 없이 설정한 DB를 읽기 전용으로 점검합니다. 운영 중이면 집계만 읽고, DB가 없거나 점검이 실패하면 상수 오류 코드를 출력하고 종료 코드 1을 반환합니다. 중단/복구 중 시장이 있으면 `DEGRADED`로 기록합니다. 정상 상태를 무결성 전체 감사나 실제 Discord 전달 성공으로 해석하지 않습니다.

봇 실행 중 금융 Worker가 60초마다 `OPERATIONAL_STATUS`를 출력합니다. 활성 시장·중단 시장·발송 대기·가장 오래된 발송 지연·미정산 배당 권리·누적 청산/교체 사건 수만 포함합니다. Gateway는 60초마다 `OPERATIONAL_METRICS`를 출력합니다. 단위는 밀리초이고 각 분포는 마지막 최대 1,024개 관찰의 p50/p95/max이며 `count`는 실행 이후 누적 개수입니다. Worker가 다시 시작되면 메모리 지표도 새로 시작합니다.

| 항목 | 의미 |
|---|---|
| `queryMs`, `financialMs`, `tickMs`, `backgroundMs` | 요청 접수부터 결과까지의 전체 시간; 오류/BUSY도 관찰 |
| `workerServiceMs` | 실제 Worker의 동기 작업 시간 |
| `queueAndTransportMs` | 전체 시간에서 작업 시간을 뺀 대기/전달 시간; OS 대기와 메시지 전달을 별도 분해하지 않음 |
| `deferMs` | 실제 비공개 초기 응답 호출 완료까지의 시간 |
| `backupMs` | 성공 생성 또는 실패한 백업 유지보수 시간; 여러 유지보수 작업을 포함할 수 있음 |
| `errors`, `gateBusy`, `databaseBusy` | 금융 오류·요청 보호 거절·SQLite BUSY/LOCKED 건수 |
| `integrityFailures`, `zeroCorporateReference` | 무결성 실패·활성 종목의 양쪽 기준가 0 충돌 |
| `discord429`, `notificationFailures`, `backupFailures` | 감지한 Retry-After·개인 발송 오류·백업 실패 |

`discord429`는 발송 계층에 전달된 Retry-After 오류만 셉니다. Discord SDK가 내부에서 처리한 모든 429나 다른 API 호출을 집계한 것으로 주장하지 않습니다. 발송 ACK 전 중단은 외부 메시지 재전송 가능성을 남기며 금융 재실행과 구분합니다.

로그는 stderr의 구조화된 집계/상수 코드입니다. 원문 Interaction·Discord ID·계좌 ID·키·SQL·예외 stack은 출력하지 않습니다. 외부 관제나 이메일/메신저 알림은 연결하지 않았습니다. 운영자는 프로세스 관리자의 로그 수집·파일 회전·용량 상한과 접근 ACL을 구성하고 운영 주체의 보유기간을 확정해야 합니다. 이 집계는 개인정보를 다루는 관리자별 접근 감사 기록을 대체하지 않습니다.

운영 점검에서는 마지막 `BACKUP_VERIFIED`·`BACKUP_MIRRORED`·`BACKUP_REHEARSAL_VERIFIED` 시각과 해당 manifest를 함께 확인합니다. 기본 주기가 지났는데 성공이 없거나 `BACKUP_FAILED`·`OPERATIONAL_STATUS_UNAVAILABLE`·`REPOSITORY_WORKER_EXITED`·`ZERO_CORPORATE_REFERENCE`·무결성 실패·지속적인 BUSY가 발생하면 아래 절차를 따릅니다. 오래된 발송 대기는 동의·플랫폼 권한·재시도 예정 시각을 확인하고 금융 거래를 재실행하여 해결하지 않습니다.

## 장애 대응

1. 발생 시각·상수 코드·집계·마지막 성공 백업 시각을 기록합니다. 토큰·키·원본 DB·개인정보를 공개 로그나 지원 메시지에 복사하지 않습니다.
2. 기록 무결성·키/장비 접근 문제가 있으면 봇과 운영 도구를 정상 종료하고 DB/WAL·백업·환경 접근을 제한합니다. 중단 시장을 임의 SQL로 활성화하거나 가격 0을 임의 최저가로 바꾸지 않습니다.
3. 디스크 용량·프로세스·잠금·서버 시계·키 접근·복제 경로 ACL을 확인합니다. 저장장치 유실이면 마지막 성공한 별도 사본 이후 손실 가능 범위를 명시합니다.
4. 일관된 사본을 검증하고 새 파일 복구 및 이후 종료/동의 철회 대조를 수행합니다. 원본을 덮어쓰거나 실제 시장을 진단용 초기화 함수로 재생성하지 않습니다.
5. 키 유출이 의심되면 관련 서비스 자격증명과 저장장치 접근을 차단하고 대응 담당자에게 제한된 채널로 전달합니다. 지속 계좌/경제/백업 키를 `.env`에서 즉석 교체하면 기존 기록을 읽지 못하므로 검증된 별도 이행 절차가 필요합니다.
6. 권리·예약·시장 시각·기준전략·성과·개인 요청 대조가 끝난 뒤 재개하고 결과를 남깁니다. 개인정보 침해의 법적 통지·신고 판단과 관리자 접속기록은 운영 주체가 확정할 별도 절차입니다.

## 재개 가능한 모형 검증

경제 모형 검증의 그림자 계좌는 최초 10,000포인트만 투입하는 고정 원금 시나리오입니다. 개인 계좌의 정기 납입은 이 실험에 넣지 않으며 실서비스 계좌와 비교할 때 자금 흐름의 차이를 구분합니다.

```powershell
npm run verify:model -- --preset pilot --max-ticks-per-run 1000 --max-seconds 60
npm run verify:model -- --preset drift-pilot --max-ticks-per-run 1000 --max-seconds 60
npm run verify:model -- --preset reference --max-ticks-per-run 1000 --max-seconds 60
npm run verify:model -- --preset drift --max-ticks-per-run 1000 --max-seconds 60
```

각 명령은 한 번의 제한된 실행입니다. 같은 preset·출력 디렉터리로 다시 실행하면 확정 checkpoint에서 이어갑니다. `reference`는 160개 보정/40개 holdout 시드×10,000틱이고 `drift`는 고정 두 시드×100,000틱입니다. 작은 pilot의 COMPLETE는 큰 배치의 완료를 의미하지 않습니다. `IN_PROGRESS`·`FAILED`도 실제 범위와 자원을 기록하며 실패 시드를 지워 다른 시드로 바꾸지 않습니다. 시간 상한은 협력적 검사로 현재 틱/원자적 checkpoint 쓰기의 시간이 추가될 수 있습니다.

결과는 `artifacts/milestone6/model-<preset>.json`, 상태는 `.model-checkpoints/<preset>`에 저장합니다. 강제 종료 뒤 `.model-validation.lock`이 남으면 기록된 PID와 해당 검증 프로세스의 종료를 먼저 확인합니다. 운영자가 그 preset의 잠금 파일 한 개와 자신의 미완성 `.tmp` 파일만 점검한 뒤 확정 index에서 재개합니다. 금융 DB의 작성자 잠금이나 완료 checkpoint를 지우지 않습니다. 결과가 잘 나오도록 preset·시드·경제 파라미터를 바꾸지 않습니다.

부하 진단은 `npm run verify:load`, 합성 백업 복구 진단은 `npm run verify:recovery`입니다. 부하는 실제 Worker에서 계좌/체결/틱을 진행하므로 모형 배치·전체 테스트 등 다른 무거운 작업과 동시에 실행한 경우 경쟁 여부를 결과에 기록합니다. 공개 가격 projection 800,000행 검사는 경제/권리/기준전략 10,000틱 생산 이력 검사를 대신하지 않습니다.
